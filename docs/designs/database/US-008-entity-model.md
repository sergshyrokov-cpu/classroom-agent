# US-008 Entity Model — AppUser and AuditEvent

Companion to `docs/designs/database/US-008-db-design.md`, which owns the columns
and constraints. This document owns the CLR types, where they live, and how they
map to business concepts and to the API DTOs of
`docs/designs/api/US-008-openapi.yaml`.

## 1. Business concepts → entities

| Business concept (`trebovaniya.md`) | Entity | Table |
|---|---|---|
| Учётная запись пользователя инсталляции — Админ или Декан (§3 "AppUser") | `AppUser` | `app_user` |
| Роль в приложении: Админ, Декан (§2) | `AppRole` | `app_user.role` |
| Способ входа: Google OAuth для Админа, логин/пароль для Декана (§2, §3) | `SignInMethod` | `app_user.sign_in_method` |
| Выбранный язык интерфейса (§5) | `UiLanguage` | `app_user.ui_language` |
| Время последнего успешного входа — от него считается срок хранения (§5 v53) | `AppUser.LastSuccessfulSignInAt` | `app_user.last_successful_sign_in_at` |
| Строка аудита: кто, когда, что, с каким исходом (§5) | `AuditEvent` | `audit_event` |
| Отказ во входе и его категория (§5 v45, v62, v64) | `AuditOutcome`, `AuditRefusalCategory` | `audit_event.outcome`, `.refusal_category` |

The Admin's `AllowedAdmin` entry stays in the **Control Plane** and is never
mirrored here (BR-012, SC-3): there is no entity for it in the installation and
no table to hold a copy.

## 2. Installation — `ClassroomAgent.Domain`

`Domain` depends on nothing (AD-3). No Identity type, no EF Core type and no
ASP.NET type appears in any of the following (spec I-2).

### 2.1 `AppUser` (`Domain.Entities`)

| Member | Type | Note |
|---|---|---|
| `Id` | `long` | surrogate key |
| `Email` | `string` | lower-cased, ≤ 254 |
| `NormalizedEmail` | `string` | lookup and uniqueness key |
| `Role` | `AppRole` | |
| `SignInMethod` | `SignInMethod` | |
| `PasswordHash` | `string?` | **null for every Admin** (S-04) |
| `SecurityStamp` | `string` | Identity-shaped, as `Owner` (US-001) |
| `ConcurrencyStamp` | `string` | EF concurrency token |
| `AccessFailedCount` | `int` | unused by the Admin path (spec I-3) |
| `LockoutEnd` | `DateTimeOffset?` | unused by the Admin path |
| `UiLanguage` | `UiLanguage` | school default at creation; US-039 lets the user change it |
| `IsDisabled` | `bool` | only US-012 sets it |
| `LastSuccessfulSignInAt` | `DateTimeOffset?` | null until the first success |
| `CreatedAt`, `UpdatedAt` | `DateTimeOffset` | stamped by the interceptor, never by hand (PC-6) |

Construction is through a factory, not a public constructor, so an Admin row
cannot be built with a password:

- `AppUser.CreateAdmin(email, normalizedEmail, uiLanguage, signedInAt)` — sets
  `Role = Admin`, `SignInMethod = Google`, `PasswordHash = null`,
  `IsDisabled = false`, `LastSuccessfulSignInAt = signedInAt`. It takes no
  password parameter at all, so S-04 holds at the type level as well as in the
  schema.
- `RecordSuccessfulSignIn(at)` — the only mutator this Story needs.
- The Dean factory arrives with US-012; this Story adds none, so no code can
  create a Dean yet.

`AppUser` holds no navigation property. The link to a `ClassroomParticipant` is
Epic 7 and is not anticipated (`package-map.md`).

### 2.2 `AuditEvent` (`Domain.Entities`)

Immutable: private setters, no public mutator, and `internal`/`private`
constructor. Built only through factories that take no free string which could
carry an email, a token or a code — the shape the Control Plane's `AuditEvent`
already established (US-001).

| Member | Type | Note |
|---|---|---|
| `Id` | `long` | |
| `OccurredAt` | `DateTimeOffset` | UTC, from `TimeProvider` |
| `ActorType` | `AuditActorType` | |
| `ActorId` | `long?` | the `AppUser` id; no navigation property, no foreign key (PC-9) |
| `ActorRole` | `AppRole?` | the role at the time of the action |
| `Action` | `AuditAction` | |
| `TargetType` | `AuditTargetType?` | unused by this Story |
| `TargetId` | `long?` | unused by this Story |
| `Outcome` | `AuditOutcome` | |
| `RefusalCategory` | `AuditRefusalCategory?` | |
| `RequestId` | `string?` | ≤ 128, generated by the host |
| `CreatedAt`, `UpdatedAt` | `DateTimeOffset` | always equal for this entity (PC-6, db-design §4.2) |

Factories, one per row this Story can write:

- `AdminSignInSucceeded(appUserId, occurredAt, requestId)`
- `AdminSignInRefused(appUserId, role, category, occurredAt, requestId)` —
  rejects a category that cannot apply to a known account
- `AdminSignInRefusedAnonymous(category, occurredAt, requestId)`

Each mirrors a row of db-design §4.4. None accepts an email.

### 2.3 Enums (`Domain.Enums`)

| Enum | Members | Stored as |
|---|---|---|
| `AppRole` | `Admin`, `Dean` | `admin`, `dean` |
| `SignInMethod` | `Google`, `Password` | `google`, `password` |
| `UiLanguage` | `Uk`, `En` | `uk`, `en` |
| `AuditActorType` | `AppUser`, `Anonymous`, `System` | `app_user`, `anonymous`, `system` |
| `AuditAction` | `AdminSignIn` | `admin_sign_in` |
| `AuditTargetType` | *(empty in this Story)* | — |
| `AuditOutcome` | `Succeeded`, `Refused` | `succeeded`, `refused` |
| `AuditRefusalCategory` | `NotInAllowedAdmin`, `ControlPlaneUnavailable`, `UnknownInstallation`, `CallbackFailed`, `AccountDisabled` | snake_case codes |

`AppRole` keeps exactly two members: Teacher and Student are Epic 7 and are not
added speculatively (`package-map.md`). `AuditAction` and `AuditTargetType` grow
in the Story that performs the action, never ahead of it (spec I-11).

Every enum is persisted as an explicit string code through `HasConversion`, never
as an integer or a CLR member name (db-design §2).

`UiLanguage` already exists in `ControlPlane.Persistence` for the Owner. It is
**not** shared: `ControlPlane` may not reference `Domain` (`package-map.md`), so
the installation declares its own with the same two members and the same codes.
That duplication is required by the dependency rules, not an oversight.

## 3. Installation — `ClassroomAgent.Infrastructure.Persistence`

### 3.1 `AppUserConfiguration` (`Persistence.Configurations`)

Implements db-design §3 exactly: `ToTable("app_user", …)` with the eight check
constraints; `HasKey(...).HasName("pk_app_user")`; `UseIdentityByDefaultColumn()`;
`HasMaxLength` on every string; `IsRequired()` matching each nullable
annotation; `PasswordHash` **not** required; `ConcurrencyStamp`
`.IsConcurrencyToken()`; `AccessFailedCount` and `IsDisabled` with their
defaults; the enum conversions of §2.3;
`HasIndex(u => u.NormalizedEmail).IsUnique().HasDatabaseName("uq_app_user_normalized_email")`.

### 3.2 `AuditEventConfiguration` (`Persistence.Configurations`)

Implements db-design §4 exactly: the ten check constraints, the enum conversions,
`RequestId` with `HasMaxLength(128)` and no index (§4.3). No relationship is
declared for `ActorId` — it is a plain `long?` column (PC-9).

### 3.3 `ClassroomAgentDbContext`

Gains `DbSet<AppUser>` and `DbSet<AuditEvent>` and picks up both configuration
classes. The existing `TimestampInterceptor` stamps both entities without change.
Nothing else in the context changes; `legitimacy_state` is untouched.

### 3.4 Repositories (`Persistence.Repositories`)

| Port (`Application/Ports`) | Implementation | Operations |
|---|---|---|
| `IAppUserRepository` | `AppUserRepository` | find by normalized email (tracked); add |
| `IAuditEventRepository` | `AuditEventRepository` | add |

Both only stage changes. Neither calls `SaveChangesAsync` — the use case owns the
transaction boundary through `IUnitOfWork` (`package-map.md`, AD-7). Neither
exposes an update or delete for `AuditEvent`: the type has no mutator and the
repository offers no way to reach one (PC-9).

## 4. Installation — `ClassroomAgent.Application`

Nothing in `Application` references EF Core or an Identity type.

| Type | Namespace | Role |
|---|---|---|
| `IAppUserRepository`, `IAuditEventRepository` | `Application.Ports` | persistence ports (AD-4) |
| `IControlPlaneClient` (+ the login-check method) | `Application.Ports` | extended, not replaced — api-design §2.1 |
| `AdminLoginCheckReply` | `Application.Models` | `Allowed`, `NotAllowed`, `UnknownInstallation`, `Unavailable` (spec FR-008) |
| `SignInOutcome` | `Application.Models` | success, or a refusal carrying its category as **data** — no user-visible string (AD-6) |
| `CompleteGoogleSignInUseCase` | `Application.UseCases` | the decision of spec FR-010; registered in `PermittedServiceWrites` against `SignInBookkeeping` and `AuditEvent` (FR-013) |

The use case is the transaction boundary: the `app_user` change and its
`audit_event` row are saved together (db-design §4.4).

## 5. Mapping to API DTOs and wire types

No entity crosses a controller or view boundary (AD-8).

| Entity / field | Travels as | Where |
|---|---|---|
| `AppUser.Email` | `LandingPageModel.email` | rendered as is, never translated (FR-017) |
| `AppUser.Role` | `LandingPageModel.role` — `Admin` \| `Dean` | |
| `AppUser.NormalizedEmail` | **nowhere** | internal lookup key only |
| `AppUser.PasswordHash`, `SecurityStamp`, `ConcurrencyStamp`, `AccessFailedCount`, `LockoutEnd` | **nowhere** | never on a DTO, a view model or an API response (SC-2, AD-8, S-04) |
| `AppUser.LastSuccessfulSignInAt` | **nowhere in this Story** | retention input only (PC-11) |
| `AuditEvent` (any field) | **nowhere** | written only; the audit viewer is EPIC-9 |
| `AdminLoginCheckReply` | never on the wire | the wire type is `AdminLoginCheckResponse { allowed }` in `Contracts`; `Infrastructure/ControlPlane` maps between them (AD-4) |
| `LegitimacyMode` (US-005) | `LandingPageModel.isReadOnly`, `.readOnlyReason`, `.lastSuccessfulCheckAt` | read through `GetLegitimacyModeQuery`, not recomputed in the view (AD-6) |

`ClassroomAgent.Contracts` gains `AdminLoginCheckRequest` and
`AdminLoginCheckResponse` and nothing else. Neither carries teaching data, school
statistics or any field beyond the installation id, the email being checked and a
yes/no answer (SC-12, S-16).

## 6. Control Plane

**No entity, enum, configuration or migration changes.** The Admin login check
reads existing `AllowedAdmin` rows through a method on the existing
`AllowedAdminRegistry` (or an equally placed service in `ControlPlane.Services`)
and writes nothing — no audit row, no `InstanceLicenseCheck` (spec FR-009, S-17;
db-design §7.2).

`Controllers` hold no rule and never touch `DbContext`; the lookup and the
comparison live in `Services`, which is the only caller of `Persistence` (AD-3).
The comparison is on the stored lower-cased email of **that** `Installation`
(SC-3, BR-079).
