# US-042 Database Design — Names of students and teachers in a template report

**Verdict: PASS.** One migration (PC-2), `ParticipantNamePartsAndTemplateNameSource`,
that:

1. adds two nullable columns to `classroom_participant` — `surname`,
   `given_name` (spec FR-001, FR-009) (§2);
2. adds one non-null column to `report_template` — `name_source`, with a check
   constraint; every existing row gets `profile` (spec FR-002, FR-009, AC-005)
   (§3).

No new table, no index, no foreign key, nothing dropped or renamed, no change to
`audit_event` (spec FR-007: no new action, no setting value). Entity and port
details: `docs/designs/database/US-042-entity-model.md`.

## 1. Decisions in one table

| # | Decision | Why |
|---|---|---|
| D-1 | Columns `surname` / `given_name`, entity properties `Surname` / `GivenName` | The spec's business terms; Google's `familyName` / `givenName` appear only in the Infrastructure adapter (AD-4). |
| D-2 | Bound **750** for each | Spec I-7: no smaller than any realistic name, as for `full_name` (US-014 db-design §4.1). Google documents no length; either part is at most the full name. |
| D-3 | Normalisation exactly as `full_name`: trim, blank → null, cut to 750 | Spec FR-001, VR-003. No case or alphabet change (v86). |
| D-4 | `name_source` as a lower-case code `varchar(8)` + check `IN ('profile','email')` | US-027 precedent for every template enum (`view`, `scale_mode`, `late_mark_kind`); codes equal the form/query values (US-042 api-design §2.1). |
| D-5 | Existing templates filled with `profile` by the migration; no lasting column default | Spec FR-009, AC-005. The domain always sets the value; a lasting database default would hide a missing assignment. |
| D-6 | No index on the new columns | Spec I-9: read with participant rows selected by membership; ordering is in `Application` (UI collation). PC-7 adds an index only for a query that filters or sorts in the database. |
| D-7 | Built-in template stays in code with `profile` | US-027 FR-006, I-1: never stored. |

## 2. `classroom_participant` — two new columns

| Column | Type | Null | Constraint | Source | Personal data |
|---|---|---|---|---|---|
| `surname` | `varchar(750)` | yes | — | Google `name.familyName` of the roster entry | **yes** |
| `given_name` | `varchar(750)` | yes | — | Google `name.givenName` of the roster entry | **yes** |

Existing columns unchanged (`full_name` stays and keeps being written — the
US-025 journal and the Meet pages use it, spec FR-001).

**Write rules (PC-10 upsert, US-014):**

- Written by the synchronization's roster upsert, on insert and on every update,
  from the roster entry: **replace**, never merge — a removed part becomes null
  (AC-001).
- A participant imported only as a submitter (US-015 OD-006) is created with
  both null; nothing changes in that path.
- The migration writes nothing into existing rows: they stay null until the next
  synchronization (spec FR-001, Story Scope). No backfill from `full_name` — the
  program does not split names (v86).

**Sensitive-data handling (PC-9, SC-10):** both columns are personal data of
students (potentially minors) and teachers, like `email` and `full_name`. Read
only into the report DTO for Admin and Dean; never written to a log line, an
audit row or an address (spec S-07). Deleted with their row by the existing
retention purge (PC-11) — no new purge rule.

## 3. `report_template` — one new column

| Column | Type | Null | Constraint | Values |
|---|---|---|---|---|
| `name_source` | `varchar(8)` | no | `ck_report_template_name_source`: `name_source IN ('profile', 'email')` | `profile`, `email` |

- Mapped from the domain enum `ReportNameSource` through an explicit value
  converter, as the US-027 enums (`ReportTemplateConfiguration`).
- Written by create, copy and change (whole replace, US-027 FR-009). Not part of
  the uniqueness key; no index.
- Not school personal data; never in an audit row (spec FR-007 — the row carries
  the template id only).

## 4. Migration `ParticipantNamePartsAndTemplateNameSource`

Generated by `dotnet ef migrations add` (PC-2) and adjusted in one place:

1. `AddColumn surname varchar(750) NULL` and `AddColumn given_name varchar(750)
   NULL` on `classroom_participant`.
2. `AddColumn name_source varchar(8) NOT NULL` on `report_template` with
   `defaultValue: "profile"` — the generated `""` is replaced by `"profile"`, so
   every existing row is `profile` (D-5).
3. `AlterColumn name_source` to drop the default again, so the schema matches the
   model (no `HasDefaultValue` in the configuration).
4. `AddCheckConstraint ck_report_template_name_source`.

`Down` drops the check, `name_source`, `given_name` and `surname`. The model
snapshot is regenerated. No `ExecuteSqlRaw`, no `EnsureCreated()`.

Backward compatibility (PC-2, §5 "Развиваемость"): additive only; a previous
release reading the table ignores the new columns.

## 5. Queries

- The report's members read (F3 of `JournalFieldSource.GetMembersAsync`) selects
  `surname`, `given_name` and `email` instead of `full_name` — same single query,
  same join, so the report's round-trip count is unchanged (spec FR-006, §9).
- The template read (`IReportTemplateRepository.GetAsync`) returns the new column
  with the row; no extra query.
- The synchronization's participant upsert writes the two columns in the update
  it already issues.
