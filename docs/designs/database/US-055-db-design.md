# US-055 Database Design — Points and grades of any size are stored as Google returned them

## 1. Scope

Three existing columns change type; nothing else in the schema changes (spec
FR-001, FR-003). No table, column, constraint, index, relationship, nullability
or identifier is added, removed or renamed. `openapi` does not exist by design
(API_DESIGN NOT_APPLICABLE); `api_design` was read instead.

## 2. What exists

From US-015 DB design (§`course_work`, §`submission`), migration
`20260929052443_AddCourseWorkAndSubmissions` and the model snapshot:

| Table | Column | Type | Null | Constraints on it |
|---|---|---|---|---|
| `course_work` | `max_points` | `numeric(10,4)` | yes | `ck_course_work_max_points_non_negative` (`max_points IS NULL OR max_points >= 0`); `ck_course_work_material_has_no_grading` |
| `submission` | `assigned_grade` | `numeric(10,4)` | yes | `ck_submission_grades_non_negative` |
| `submission` | `draft_grade` | `numeric(10,4)` | yes | `ck_submission_grades_non_negative` |

None of the three columns is part of an index (`SubmissionConfiguration.cs:69–76`,
`CourseWorkConfiguration.cs:63–67`). No raw SQL outside the configurations and
the migration names them (grep of `src/`).

## 3. Change

### 3.1 Column type

All three columns become **unconstrained `numeric`** (no precision, no scale).
Nullability stays `NULL`. The three CHECK constraints stay as they are, by name
and text.

Why unconstrained `numeric` (spec I-2):

- It holds every value of the CLR type `decimal` (≤ 28–29 significant digits,
  scale ≤ 28) exactly, with no overflow and no rounding — FR-001's property.
  PostgreSQL `numeric` without typmod allows up to 131 072 digits before the
  point and 16 383 after.
- A constrained `numeric(p,s)` large enough for every `decimal` would itself be
  a limit to argue about and, if `s` changed, would rewrite the table (§4).
- `double precision` is rejected: it rounds decimal fractions (10.123456 is not
  stored exactly) and would break FR-002 / VR-002.

Explicit mapping (PC: every persistent property configured explicitly):

```csharp
// CourseWorkConfiguration.cs
builder.Property(c => c.MaxPoints).HasColumnType("numeric");
// SubmissionConfiguration.cs
builder.Property(s => s.AssignedGrade).HasColumnType("numeric");
builder.Property(s => s.DraftGrade).HasColumnType("numeric");
```

The CLR types stay `decimal?`; no entity, value object or DTO changes
(entity model).

### 3.2 Migration `WidenGradeColumns`

One EF Core migration (PC-2) generated by
`dotnet ef migrations add WidenGradeColumns`, with the model snapshot updated.

`Up` — three `AlterColumn<decimal>` calls, `type: "numeric"`,
`oldType: "numeric(10,4)"`, `nullable: true`, `oldNullable: true`. The SQL is
`ALTER TABLE … ALTER COLUMN … TYPE numeric;` with no `USING` clause: the cast is
the implicit `numeric → numeric` one, so every stored value and every null stays
unchanged (AC-005).

`Down` — the reverse `AlterColumn` to `numeric(10,4)`. It is lossy by nature: it
rewrites the tables, rounds to four decimal places, and **fails with 22003** if
any stored value exceeds 999 999.9999. It exists only because EF Core migrations
are reversible by default; no deployment step runs it.

No data migration, no `EnsureCreated()`, no SQL outside the migration.

## 4. Table rewrite and lock time (spec §9)

**No table rewrite.** Removing the typmod from a `numeric` column is
binary-compatible in PostgreSQL: the on-disk value does not change, so
`ALTER COLUMN … TYPE numeric` updates the catalog only.

**What is scanned.** Because the three CHECK constraints depend on the altered
columns, PostgreSQL re-validates them, which is one sequential read of the
table. No index is rebuilt (none covers these columns).

**Lock.** Each `ALTER TABLE` takes an `ACCESS EXCLUSIVE` lock on its table for
that read. The migration runs as the explicit deployment step
(`persistence-conventions.md`, migrations not applied at startup), so no
synchronization or Dean request runs against the table at the time.

**Measured** (2026-10-25, `postgres:17-alpine` — the image TC-2 tests use —
synthetic table of 2 000 000 rows, 95 MB, with the same CHECK constraint):

| Step | Time |
|---|---|
| `ALTER COLUMN assigned_grade TYPE numeric` | 154 ms |
| `ALTER COLUMN draft_grade TYPE numeric` | 127 ms |
| `pg_relation_filenode('submission')` before / after | 16385 / 16385 — not rewritten |
| rows whose value changed (`<> round(…, 4)`) | 0 |
| insert and read back 12345678.5 and 10.123456 | stored exactly |

For the rehearsal's 821 810 submissions this means well under one second of
lock; `course_work` is smaller still. The figures are for a developer machine;
the pilot server may be slower, but not by the orders of magnitude that would
matter.

## 5. Storage

`numeric` stores a value by its digits, not by its declared typmod, so a value
of ordinary size (e.g. 12, 7.5) takes the same bytes before and after. Only a
genuinely longer value takes more. No measurable growth (spec §9).

## 6. Sensitive data

Grades and maximum points are student data (S-03). The design changes how much
of a value fits, not who can read it, where it is copied or how long it is kept
(retention purge and erasure on request, US-038, are unchanged —
`ParticipantErasureReadSource` only tests the columns for `NULL`). The probe in
§4 used synthetic values only; no real value was read.

## 7. Tests this design asks for (for TEST_WRITING)

- **AC-005 migration.** On real PostgreSQL: migrate to the migration before
  `WidenGradeColumns`, insert synthetic rows (four-decimal values, the old
  maximum 999 999.9999, zero and nulls in each column), apply
  `WidenGradeColumns`, and assert every value and null is unchanged.
- **Column type.** After all migrations, `information_schema.columns` reports
  `data_type = 'numeric'` with `numeric_precision` and `numeric_scale` both
  `NULL` for the three columns.
- **Round trip (AC-001 … AC-003).** Values above 999 999.9999 and with more than
  four decimal places save and read back equal (VR-002).
- **Constraints kept.** A negative grade or maximum is still rejected by the
  existing CHECK constraints.
- **Model matches migrations.** The existing installation checks
  (`HasPendingModelChanges()` in `InstallationDatabaseTests` and others) stay
  green with the snapshot updated.
