# US-027 Database Design — Report templates and the on-screen report

**Verdict: PASS.** One migration (PC-2) that:

1. adds the created-template aggregate — `report_template` with two child tables,
   `report_template_mark` and `report_template_scale_row` (§2);
2. adds one nullable column to the mirror, `course_work.scheduled_time`
   (spec FR-020, OD-004 a) (§3);
3. widens the `audit_event` value checks by three actions and one target type and
   adds one shape check (§4).

No data migration, no index on an existing table, nothing dropped or renamed.
`trebovaniya.md` v85 (host-wide `Cache-Control: no-store`) has no persistence
effect. Entity details: `docs/designs/database/US-027-entity-model.md`.

## 1. Decisions in one table

| Question the spec left to this stage | Decision | § |
|---|---|---|
| Shape of "one new table … with its scale rows and state marks" (FR-018) | one aggregate: a root table and two child tables owned by it | 2 |
| Author reference that never blocks the purge (FR-014) | bare `author_id`, **no foreign key**, never cleared — the PC-11 rule for rows that name an account | 2.1 |
| Unique name, trimmed and case-insensitive (VR-001, I-14) | stored `normalized_name` with a unique index, Identity-style | 2.1 |
| Index for "items of a course by lesson date" (FR-018) | **no new index**: the course-prefixed indexes of US-015 bound the read to one course's items | 5.2 |
| "Last change" of a template (FR-002) | `report_template.updated_at`; the change path marks the root modified | 2.4 |
| Concurrency (I-11) | no concurrency token: last save wins | 2.5 |

## 2. The template aggregate

All three tables are **school-own data** (v83 second layer): they reference
nothing in the mirror and nothing in the mirror references them. They hold no
student data and no copy of the author's name or email (spec S-14). They are not
touched by the retention purge (PC-11 lists course data, leavers, Meet, accounts
and audit only); a template lives until a user deletes it.

### 2.1 `report_template`

| Column | Type | Null | Rule | Source |
|---|---|---|---|---|
| `id` | `bigint` identity | no | PK `pk_report_template` (PC-3) | — |
| `name` | `varchar(100)` | no | trimmed school text, as written; 1–100 chars validated in `Application` | VR-001, I-13 |
| `normalized_name` | `varchar(100)` | no | `name` upper-cased invariant (`ToUpperInvariant`), set only by the entity; unique `uq_report_template_normalized_name` | VR-001, I-14 |
| `view` | `varchar(8)` | no | check `ck_report_template_view`: `IN ('full','short')` | FR-003, BR-057 |
| `hide_materials` | `boolean` | no | — | FR-003 |
| `hours_per_lesson` | `integer` | no | check `ck_report_template_hours_per_lesson`: `BETWEEN 1 AND 10` | VR-005, I-16 |
| `scale_mode` | `varchar(8)` | no | check `ck_report_template_scale_mode`: `IN ('none','ranges')` | FR-015, VR-004 |
| `late_mark_kind` | `varchar(8)` | no | check `ck_report_template_late_mark_kind`: `IN ('program','own','hidden')` | FR-003, VR-003 |
| `late_mark_text` | `varchar(30)` | yes | check `ck_report_template_late_mark_text`: `(late_mark_kind = 'own') = (late_mark_text IS NOT NULL)` | VR-003 |
| `author_id` | `bigint` | no | the creating `AppUser.Id`; **no FK, no index** | FR-014 |
| `created_at`, `updated_at` | `timestamptz` | no | interceptor-stamped (PC-6) | PC-6 |

**Author.** `author_id` follows PC-11 exactly: "rows that name an account …
keep the internal id without a foreign key, so the deletion never cascades or
blocks". The purge deletes `app_user` rows unchanged; a template whose author
row is gone reads as `AccountDeleted` (spec AC-014) — "the id has no `app_user`
row" *is* the deleted state, so nothing has to clear the column and the purge
needs no new step. Identity values are never reused (`GENERATED BY DEFAULT AS
IDENTITY`, no sequence reset in any convention), so a dangling id never comes
to name another account. No index: nothing looks templates up by author.

The spec's example ("a nullable reference cleared by the purge") was considered
and rejected: it adds an FK with `SET NULL` — a cascade PC-8 asks to justify —
and a second representation of "author unknown" (null and missing row) for the
same state.

**Name uniqueness.** `Application` checks `normalized_name` before writing to
give the `NameNotUnique` message (api-design §3); the unique index is the
backstop against two concurrent saves. `UnitOfWork` translates a violation of
exactly `uq_report_template_normalized_name` into an `Application` exception
(precedent: `uq_app_user_normalized_email`, US-012), which the use case maps to
the same `NameNotUnique` field error. Invariant upper-casing is the comparison
ASP.NET Core Identity uses for emails; it is culture-independent and folds
Cyrillic and Latin case alike. No PostgreSQL collation or `citext` (both depend
on what is installed on each school's server; no package change).

The built-in template's name is not reserved (I-14) and has no row: no check
against it.

### 2.2 `report_template_mark`

One row per cell state of spec FR-003 — exactly nine per template.

| Column | Type | Null | Rule |
|---|---|---|---|
| `id` | `bigint` identity | no | PK `pk_report_template_mark` |
| `report_template_id` | `bigint` | no | FK `fk_report_template_mark_report_template` → `report_template`, **`ON DELETE CASCADE`** |
| `state` | `varchar(32)` | no | check `ck_report_template_mark_state`: `IN ('turned_in_not_graded','returned_without_grade','turned_in','returned','not_turned_in','not_due_yet','not_turned_in_no_due_date','not_assigned','unrecognised')` |
| `kind` | `varchar(8)` | no | check `ck_report_template_mark_kind`: `IN ('program','own','empty')` |
| `text` | `varchar(30)` | yes | check `ck_report_template_mark_text`: `(kind = 'own') = (text IS NOT NULL)` |
| `created_at`, `updated_at` | `timestamptz` | no | PC-6 |

Unique `uq_report_template_mark_template_state (report_template_id, state)` —
also the FK index (PC-7, leading column).

**Completeness** (all nine states present) is an invariant of the entity
(`ReportTemplate.Create` / `Change` take a complete set and throw otherwise), not
a database constraint: SQL cannot count child rows in a check. The unique index
guarantees no state twice.

**Why rows, not eighteen columns.** A child row per state keeps the root narrow,
lets one mapping and one check serve all nine states, and lets a later program
version add a state with one new allowed value plus default rows in its
migration. Model verified to build with EF Core 10 / Npgsql 10 and the snake-case
convention (scratch model, this stage).

### 2.3 `report_template_scale_row`

Present only when `scale_mode = 'ranges'` (1 … 101 rows); none with `'none'`
(VR-004: rows sent with "no conversion" are not stored).

| Column | Type | Null | Rule |
|---|---|---|---|
| `id` | `bigint` identity | no | PK `pk_report_template_scale_row` |
| `report_template_id` | `bigint` | no | FK `fk_report_template_scale_row_report_template` → `report_template`, **`ON DELETE CASCADE`** |
| `from_percent` | `smallint` | no | check `ck_report_template_scale_row_bounds`: `from_percent BETWEEN 0 AND 100 AND to_percent BETWEEN 0 AND 100 AND from_percent <= to_percent` |
| `to_percent` | `smallint` | no | (same check) |
| `label` | `varchar(10)` | no | school text, as written; 1–10 chars validated in `Application` |
| `created_at`, `updated_at` | `timestamptz` | no | PC-6 |

Unique `uq_report_template_scale_row_template_from (report_template_id,
from_percent)` — also the FK index. Rows that cover 0–100 without gap or overlap
(VR-004) necessarily have distinct `from` values, so the order of the table is
`from_percent` and no position column is stored. Coverage itself is validated in
`Application` and guarded by the entity; it is not expressible as a check.

"Ranges with zero rows" and "no conversion with rows" cannot be stopped by a
check either; the entity refuses both.

### 2.4 Writes and timestamps

- **Create** (from scratch or copy): one root, nine marks, 0–101 scale rows,
  inserted in one `SaveChanges`. The audit row needs the generated id
  (spec FR-016), so inside `IUnitOfWork.ExecuteInTransactionAsync` the use case
  saves the template first, then adds the audit row with `template.Id` and saves
  again; one transaction (AD-7).
- **Change**: the root is loaded **tracked** with its marks and scale rows. The
  entity overwrites the root's columns, updates each mark row **in place by
  state**, and **replaces** the scale rows (clears the collection, adds the new
  rows). Removed rows are orphans of a required relationship and are deleted by
  EF Core; the new rows are inserted. Two rows of one template may briefly share a
  `from_percent` across a delete and an insert; EF Core orders the delete first
  because the unique index is in the model — a test proves a change that keeps
  every `from` value but changes labels saves (§7).
- **`updated_at` of the root** is the template's "last change" (FR-002). A change
  that touches only child rows would leave the root `Unchanged`, so the
  interceptor would not stamp it. The repository's change path therefore marks the
  root entry `Modified` before saving; the interceptor stamps it (PC-6 — still
  never by hand in a use case).
- **Delete**: the root is deleted; `ON DELETE CASCADE` removes its marks and
  scale rows in the same statement. The cascade is justified under PC-8: the child
  rows are parts of the template, not data with a life of their own, and contain
  no student data. The audit row is written in the same transaction.

### 2.5 Concurrency

No concurrency token (spec I-11: last save wins whole). A change loads the
template tracked; not found → `404` before anything is written. If another user
deletes the template between that load and the commit, the `UPDATE` affects no
row and EF Core raises a concurrency exception, which reaches the single
exception handler (`500`, error page, nothing stored — API-10). The window is a
fraction of a second on an action used rarely; no handling is designed.

## 3. `course_work.scheduled_time` (FR-020, OD-004 a)

| Column | Type | Null | Rule |
|---|---|---|---|
| `scheduled_time` | `timestamptz` | yes | Google's `scheduledTime`, UTC (PC-6), for both resources |

- Not added to `ck_course_work_material_has_no_grading`: a material may be
  scheduled; scheduling is not grading.
- Written by `CourseWork.Import` and `CourseWork.UpdateFrom` through
  `CourseWorkDetails`, from the value the Google adapter already reads for
  `item_date` (`GoogleClassroomReader`, `ScheduledTimeDateTimeOffset`). No new
  field is requested from Google; no scope changes (SC-6).
- **Back-fill.** Confirmed in code: `RunSynchronizationUseCase` calls
  `CourseWork.UpdateFrom` for every existing item of every course it imports, on
  every run (US-015 FR-010). Rows imported before this Story therefore get their
  `scheduled_time` on the next run; until then it is null and the lesson date is
  `creation_time` (spec FR-020). No data migration.
- `item_date`, its cascade and the journal of US-025 are unchanged.
- Personal data: no. It is a date of a teacher's post.

## 4. `audit_event`

New enum members and codes (spec FR-016, api-design §8):

| Enum | Member | Code |
|---|---|---|
| `AuditAction` | `ReportTemplateCreated` | `report_template_created` |
| `AuditAction` | `ReportTemplateChanged` | `report_template_changed` |
| `AuditAction` | `ReportTemplateDeleted` | `report_template_deleted` |
| `AuditTargetType` | `ReportTemplate` | `report_template` |

The migration drops and re-creates `ck_audit_event_action` and
`ck_audit_event_target_type_value` with the new values appended, and adds:

```sql
-- ck_audit_event_report_template_shape
action NOT IN ('report_template_created', 'report_template_changed', 'report_template_deleted')
OR (actor_type = 'app_user'
    AND target_type = 'report_template'
    AND (refusal_category IS NULL OR refusal_category = 'read_only_mode')
    AND (outcome <> 'succeeded' OR target_id IS NOT NULL)
    AND (action <> 'report_template_created' OR outcome = 'succeeded' OR target_id IS NULL))
```

It encodes FR-016 and api-design §2.6: a user's action; the target type is always
`report_template`; the only refusal is read-only mode; a succeeded row names the
template; a refused create names none; a refused change or delete may name an id
or none (null for the built-in key or a malformed reference). `actor_role` is
already required for `app_user` by `ck_audit_event_actor_role`. No column is
added; no template text reaches the table (SC-11, PC-9). No index (the table's
existing `ix_audit_event_occurred_at` serves the purge).

## 5. Reads

### 5.1 The journal-field port — `IJournalFieldSource`

A new read port (spec FR-004), implemented in `Infrastructure` next to
`JournalSource`. Every query is `AsNoTracking()`, unordered (orders are applied
in `Application`, as US-025 db-design §2), with UTC bounds.

| # | Query (logical SQL) | Index used |
|---|---|---|
| F1 | `SELECT id, name, section FROM course` | none — whole table (US-025 §3.2) |
| F2 | `SELECT id, resource, title, max_points, due_at, COALESCE(scheduled_time, creation_time, item_date) AS lesson_date FROM course_work WHERE course_id = @c AND COALESCE(scheduled_time, creation_time, item_date) >= @start AND COALESCE(…) < @end` | `course_id` prefix of `ix_course_work_course_item_date` |
| F3 | `SELECT m.participant_id, m.role, m.first_seen_at, m.last_seen_at, m.on_roster, p.full_name, p.email FROM course_membership m JOIN classroom_participant p ON p.id = m.participant_id WHERE m.course_id = @c` | `uq_course_membership_course_participant`; `pk_classroom_participant` |
| F4 | `SELECT s.id, s.course_work_id, s.participant_id, s.update_time, s.state, s.raw_state, s.assigned_grade, s.draft_grade, s.turned_in_at, s.late FROM submission s JOIN course_work w ON w.id = s.course_work_id WHERE w.course_id = @c AND <F2's lesson-date predicate>` | as F2 → `ix_submission_course_work_participant` |

- **The lesson-date rule lives in one place:** the port's query expression
  `ScheduledTime ?? CreationTime ?? ItemDate` (EF Core translates it to
  `COALESCE`), used for both the filter and the projected `LessonDate`. This is
  spec FR-004's "filled today from" — the port is where journal fields are filled
  (§3 v84) — and `Application` never recomputes it. Including the deleted items
  as the journal does (spec FR-005.1): there is no deletion filter in the mirror.
- **F3 returns both roles** in one query; `Application` splits students (rows,
  BR-051) from teachers (FR-005.5, I-6) and applies the period rule to both.
- **Short-circuits** as US-025: no item → F3 and F4 are not issued; no
  membership → F4 is not issued.
- **Consistency between queries** is tolerated exactly as US-025 db-design §2.1.
- `IJournalSource` and the US-025 journal page are not changed.

### 5.2 Why no new index for the lesson date

The lesson date is an expression over three columns. The options were:

| Option | Rejected because |
|---|---|
| expression index on `(course_id, COALESCE(…))` | not declarable in the EF Core model — only as raw SQL in a migration, which the model snapshot does not know (PC-2, PC-4) |
| stored generated `lesson_date` column + index | a second mirror column, against spec FR-018 "the mirror changes by one column only" |
| a `lesson_date` column written by the import | the same, and a data migration for existing rows, against FR-020 |

None is needed. F2 and F4 are bounded **by the course**: both start from the
`course_id` prefix of an existing index and evaluate the date predicate on that
course's items only. US-025 db-design §4 sizes a course at a few hundred items
per school year; even a course kept for several years holds low thousands, so
the read is a short index range plus a filter on rows already in memory — the
period would narrow nothing that matters at that size. Should a
later Story need lesson dates across courses, it adds its own index.

### 5.3 Template reads — `IReportTemplateRepository`

| # | When | Query | Index |
|---|---|---|---|
| T1 | the list; the report page's drop-down | `SELECT t.id, t.name, t.updated_at, u.email FROM report_template t LEFT JOIN app_user u ON u.id = t.author_id` | `pk_app_user` |
| T2 | report, copy form, change form, change save, delete | the root by `id` with its marks and scale rows (`AsSplitQuery`: root, marks, rows — three statements, no cartesian product); tracked for change and delete, untracked otherwise | `pk_report_template`; `uq_report_template_mark_template_state`; `uq_report_template_scale_row_template_from` |
| T3 | create / change save | `SELECT EXISTS (… WHERE normalized_name = @n AND id <> @self)` | `uq_report_template_normalized_name` |

- T1 is a manual join on `author_id` (there is no navigation, no FK). A null
  `email` is `AccountDeleted`; the email is shown as is (I-10).
- The built-in template is never read from the database (spec FR-006, I-1).
- **Report request round trips:** F1, T1, T2 (three; none for the built-in), F2,
  F3, F4 — **at most eight, fixed**, whatever the rows and columns (spec FR-004,
  NFR-003). The confirmation page of a delete reads T2's root only.

## 6. Sensitive data

- No column of this Story holds personal data of a student or teacher, a
  credential, a key or a secret reference (PC-9).
- `author_id` is an internal id; the author's email is read at display time from
  `app_user`, never copied (spec S-14).
- `name`, mark texts and scale labels are school text. They are never logged and
  never written to `audit_event` (SC-10, SC-11); a log line carries template ids
  only (spec FR-019).
- `course_work.scheduled_time` is not personal data.

## 7. Schema initialisation and tests the design implies

One migration in `src/ClassroomAgent.Infrastructure/Persistence/Migrations/`
(name indicative `ReportTemplates`), generated from the model; no
`EnsureCreated()`, no hand SQL beyond what the model emits (the check constraints
are model-declared). Backward compatible: only additions, the two widened checks
accept every existing value.

Persistence facts TEST_WRITING should prove against PostgreSQL (TC-2):

- a template round-trips: root, nine marks, scale rows ordered by `from_percent`;
  `ranges` with the 12-point preset; `none` with no rows;
- two names differing only in case or surrounding spaces violate
  `uq_report_template_normalized_name` and surface as `NameNotUnique`, not `500`;
- a change that alters only one mark advances `updated_at`; a change replacing
  scale rows with the same `from` values but other labels saves;
- delete removes the child rows (cascade) and nothing else;
- the purge deletes an author's `app_user` row with a template present, the
  template survives and lists as `AccountDeleted` (AC-014);
- the check constraints refuse: an `own` mark without text and text with a
  non-`own` kind; an unknown state; hours 0 and 11; a scale row with
  `from > to` or outside 0–100; an audit row of the three actions with another
  target type, another refusal category, or a succeeded row without an id;
- `scheduled_time` is written on import and on update, null when Google sends
  none, for both resources; F2 places an item by `scheduled_time`, else
  `creation_time`, else `item_date` (AC-012), and F4 follows F2's set;
- the migration applies to a database holding US-025-era rows.

## 9. Findings

Non-blocking, for the human at the next review:

- **N-1 Spec FR-018 wording.** "One new table … with its scale rows and state
  marks" is read as one new *aggregate*: a root table and two child tables
  (§2). A variable list of up to 101 scale rows cannot live in one relational
  row without a JSON column, which would lose the per-row checks.
- **N-2 Author mechanism.** Bare `author_id` without FK (PC-11 rule) instead of
  the spec's example of a nullable reference cleared by the purge (§2.1). Same
  behaviour for the user; the purge is untouched.
- **N-3 No index for the lesson date** (§5.2), justified by per-course bounding.
- **N-4 Delete–save race ends in `500`** (§2.5), by I-11.
