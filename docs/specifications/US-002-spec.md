# US-002 Specification — Register an Installation

## 1. Overview

The second Control Plane Story. The signed-in Owner registers each school as an
`Installation` and keeps those records correct:

- a list of installations;
- a registration form (name, domain, client ID) — status "active", identifier
  generated by the Control Plane;
- a detail page showing the identifier the Owner copies into the installation's
  configuration;
- correcting the name and changing the service-account client ID;
- uniqueness of domain and client ID, enforced under concurrency;
- three new Control Plane audit events;
- Ukrainian and English translations for everything shown.

Sources: `trebovaniya.md` v69 §3 (`Installation` and its record rules), §4
(Epic 8), §5 (audit list, installation id as required configuration), §8
(antiforgery, error page, validation), §9 (Owner role, key rotation, three control
points); `security-conventions.md` SC-4, SC-10, SC-11, SC-12, SC-13;
`api-conventions.md` API-4, API-5, API-8; `architecture.md` AD-1, AD-3, AD-8,
AD-9; `persistence-conventions.md` PC-2, PC-3, PC-6, PC-9;
`deployment-conventions.md` DC-2, DC-3; BR-020, BR-021, BR-023; NFR-073. The
US-001 host baseline (deny-by-default, global antiforgery, setup gate, error page,
session, localization) is reused, not re-specified.

**All Open Decisions are resolved.** OD-001 … OD-003 were resolved by the human
on 2026-09-16, each with its recommended option, and interpretations I-1 … I-10
were confirmed (section 11); the requirements below state those resolutions.

## 2. Business Goal

The `Installation` is the source of truth for which schools exist and with which
Google Workspace domain each may work (BR-020). Every later EPIC-8 and EPIC-6
Story depends on it: `AllowedAdmin` entries attach to it (US-003), suspension
acts on it (US-004), and an installation names itself in the legitimacy check by
its identifier (US-005). One domain belongs to exactly one record, so the
program cannot spread to a domain the Owner did not register (`trebovaniya.md`
§9, v69).

## 3. Business Flow

### 3.1 Registering a school (DC-2 steps 3, 4, 6)

1. The Owner creates the school's service account in Google Cloud (outside the
   system) and notes its numeric Unique ID — the client ID.
2. The signed-in Owner opens the installations list and chooses to register one
   (FR-001, FR-002).
3. They enter the school's name, its Google Workspace domain and the client ID
   and submit (FR-003).
4. The `Installation` is created active with a generated identifier; the creation
   is audited; the Owner lands on its detail page (FR-004, FR-009).
5. The Owner copies the identifier into the installation's configuration when
   deploying it (FR-005; the installation reading it is US-005).

### 3.2 Correcting a record

- A typo in the name: the Owner submits the corrected name (FR-006).
- The service account was recreated: the Owner submits the new client ID; the
  school's super-admin must authorize delegation for it again (FR-007).
- The domain is never edited; moving a school to another domain is a new
  `Installation` (BR-021). No record is ever deleted.

## 4. Functional Requirements

### FR-001 Installations list

- Reachable only by the signed-in Owner.
- Shows every `Installation` — no status filter — each row with name, domain,
  status and creation date; each row links to its detail page.
- Status is a translated label: "active" or "suspended" (the only two values,
  `trebovaniya.md` §3). This Story only ever creates "active"; the label for
  "suspended" exists so US-004 needs no list change.
- Creation date display: date and time to the minute in UTC, marked "UTC", in
  the Owner's UI-language format (**OD-003**, resolved).
- Order: by name, case-insensitive, then by domain *(interpretation I-1)*.
- Not paginated *(interpretation I-2)*.
- With no installations: a translated "no schools registered yet" message and
  the action to register one.
- The list always offers the action to register an installation.

### FR-002 Home page

- The home page of US-001 (FR-013 there, interpretation I-8) gains a link to the
  installations list. Otherwise unchanged *(interpretation I-3)*.

### FR-003 Registration

**GET** — shows the registration form: name, domain, client ID, and the
antiforgery token. No status field (AC-002).

**POST** — each step runs only if the previous one passed:

1. **Antiforgery** — global validation of US-001 (FR-015 there). Missing or
   invalid token: `400`, error page "page expired"; nothing created.
2. **Field validation at binding** — VR-001, VR-002, VR-003. On failure: `400`,
   the form is shown again with each failed field named and why, keeping the
   values typed (AC-003); nothing created, not audited, values not logged.
3. **Normalization** — the domain is converted to lower case (VR-002). Nothing
   else is trimmed or altered.
4. **Uniqueness** — if another `Installation` (any status) has the same domain or
   the same client ID: `409`, the form is shown again with the error on the
   conflicting field(s) (FR-008); nothing created, not audited.
5. **Create** — FR-004.

### FR-004 Installation creation

In one transaction in `ControlPlane.Services` (AD-3, AD-7):

- a new `Installation` with:
  - **identifier** — a random UUID (version 4, from a cryptographically secure
    source) generated by the Control Plane; never supplied by the request, never
    changed afterwards (`trebovaniya.md` §3, v69);
  - **name** — as submitted;
  - **domain** — as normalized in FR-003 step 3;
  - **client ID** — as submitted;
  - **status** — "active";
  - **creation time** — the current UTC instant (PC-6);
- the audit row "Installation created" (FR-009).

After commit: redirect (`302`, post/redirect/get) to the new installation's
detail page *(interpretation I-4)*.

The UUID identifier is the identifier shown to the Owner, used in URLs and later
carried by the service channel. Whether it is also the primary key or an
additional uniquely-indexed column beside the PC-3 `long` key, and which internal
id audit rows carry, is `db-designer`'s decision; either way the identifier is
unique and immutable.

### FR-005 Detail page

- Route identifies the installation by its UUID identifier *(interpretation
  I-5)*.
- Shows: identifier, name, domain, status label, creation date (as FR-001,
  OD-003), client ID.
- **Identifier copy** — a control copies the identifier to the clipboard in one
  action; the identifier is also shown as selectable text, so copying works
  without the control *(interpretation I-6)*. Next to it a translated note says
  the identifier goes into the installation's configuration at deployment and
  that an installation without it does not start (`trebovaniya.md` §5, v69; DC-3).
- **Actions** — "correct name" (FR-006) and "change client ID" (FR-007).
- **No** control to edit the domain, to change the status, or to delete the
  installation. Suspending and resuming arrive with US-004.
- An identifier that does not exist, or a route value that is not a UUID:
  `404` with the translated error page (US-001 FR-016) — the same response for
  both cases.
- Every value the Owner entered (name, domain, client ID) is shown as stored and
  never translated, HTML-encoded by the view.

### FR-006 Correcting the name

**GET** — form with the current name and the antiforgery token.
Unknown installation: `404` as in FR-005.

**POST** — each step runs only if the previous one passed:

1. Antiforgery (as FR-003 step 1).
2. Installation exists — else `404`.
3. Field validation — VR-001. On failure: `400`, form again with the error and the
   typed value.
4. **Unchanged** — the new name is ordinally equal to the stored one: nothing is
   written, no audit row; redirect to the detail page (AC-006).
5. **Update** — in one transaction: only the name changes; audit row "Installation
   renamed" (FR-009). No uniqueness check: names are not unique (`trebovaniya.md`
   §3, v69). Redirect to the detail page.

Allowed whatever the installation's status *(interpretation I-7)*.

### FR-007 Changing the client ID

**GET** — form with the current client ID, the antiforgery token and a translated
explanation: the client ID changes only when the service account was recreated;
afterwards the school's super-admin must authorize domain-wide delegation for the
new client ID; the installation picks up the new value no later than its next
legitimacy check, within 6 hours (`trebovaniya.md` §9, v43, v54). Unknown
installation: `404`.

**POST** — each step runs only if the previous one passed:

1. Antiforgery.
2. Installation exists — else `404`.
3. Field validation — VR-003. On failure: `400`, form again.
4. **Unchanged** — equal to the stored client ID: nothing written, no audit row;
   redirect to the detail page (AC-007).
5. **Uniqueness** — another installation has this client ID: `409`, form again
   with the error on the field (FR-008); nothing changed, not audited.
6. **Update** — in one transaction: only the client ID changes; audit row
   "Installation client ID changed" (FR-009). Redirect to the detail page.

Allowed whatever the installation's status *(interpretation I-7)*.

### FR-008 Uniqueness under concurrency

- Domain: unique across **all** installations, active and suspended, compared in
  lower case — guaranteed because every stored domain is lower case (VR-002).
- Client ID: unique across all installations, compared ordinally.
- The guarantee is enforced by the database so that two transactions cannot both
  commit the same domain or client ID (the mechanism is `db-designer`'s), not by
  the pre-check alone.
- A request that loses the race — its insert or update rejected by that
  constraint — gets exactly the `409` response of FR-003 step 4 or FR-007 step 5,
  never `500`; its transaction, audit row included, is rolled back entirely
  (AC-004).
- Conflict messages (translated):
  - domain — "this domain is already registered to another installation. A school
    returning to its former domain is resumed, not registered again";
  - client ID — "this client ID is already registered to another installation".
  - They name no other installation (no name, no identifier) *(interpretation
    I-8)*.
- When both domain and client ID conflict, both fields carry their error.

### FR-009 Audit events

The Control Plane `AuditEvent` table exists (US-001). This Story adds exactly:

| Event | Actor (id, role) | Target | Outcome |
|---|---|---|---|
| Installation created | Owner account id, `Owner` | `Installation`, its internal id | succeeded |
| Installation renamed | Owner account id, `Owner` | `Installation`, its internal id | succeeded |
| Installation client ID changed | Owner account id, `Owner` | `Installation`, its internal id | succeeded |

- Every row carries UTC timestamp, actor, action, target, outcome and the request
  identifier (`trebovaniya.md` §5).
- **No** name, domain or client ID — neither old nor new — in any column (SC-11,
  PC-9).
- The row is written in the same transaction as the change: no change without its
  row, no row without its change (AC-008).
- Refused submissions (validation, uniqueness, unchanged value, antiforgery,
  unknown installation) write no row: `trebovaniya.md` §5 lists completed
  actions, and no refusal category exists for them (AC-008).
- Rows are never updated or deleted; kept indefinitely (SC-11, US-001 FR-012).

### FR-010 Authorization

- Every endpoint of this Story requires the signed-in Owner, declared by the
  Owner policy; none is anonymous and none is added to the SC-4 anonymous list or
  to the antiforgery exemption list (SC-4, API-9).
- A request without a session is redirected to the sign-in page; nothing is shown
  or changed (AC-009).
- While no Owner account exists, the US-001 setup gate redirects these endpoints
  to the setup page, like any other.
- The US-001 endpoint-enumeration test covers the new endpoints without a special
  case (TC-5). The Control Plane has one role, so the "forbidden role" case of
  TC-5 is the unauthenticated request.

### FR-011 GET safety and antiforgery

- Registration, name correction and client ID change are POST; GET shows forms
  and pages only and changes nothing (API-4).
- Antiforgery is the host's global validation (US-001 FR-015); a missing or
  invalid token is `400` with the "page expired" error page (AC-010).

### FR-012 Persistence

- New Control Plane entity `Installation` in `ControlPlane.Persistence`, with its
  EF Core migration in the Control Plane project (PC-2, DC-4); applied by
  deployment, never at startup.
- Holds only: identifier, name, domain, status, creation time, client ID
  (`trebovaniya.md` §3), plus the technical timestamps and key the persistence
  conventions require. **No** service-account key, key reference, secret or
  anything teaching-related (PC-9, SC-12).
- Unique constraints on domain and client ID (FR-008); unique identifier.
- Status is stored as a closed set of two values: active, suspended.
- Times are UTC (PC-6). Exact schema: `db-designer`.
- New audit action codes and the target type `Installation` extend the existing
  Control Plane audit vocabulary.
- No delete path exists: no use case, endpoint or repository method deletes an
  `Installation` (`trebovaniya.md` §3, v69).

### FR-013 Localization

- Every page, label, note, button and message of this Story comes from
  `ClassroomAgent.ControlPlane.Localization`, each key in Ukrainian and English
  (NFR-073, TC-8). Shown in the Owner's UI language, Ukrainian by default.
- Values the Owner entered are never translated (AC-011).

### FR-014 Logging

- Log lines written by these actions carry internal identifiers only — never the
  name, domain or client ID, whether valid, rejected or conflicting (SC-10, DC-10).

## 6. Validation Rules

Declared with DataAnnotations on request types; custom rules as
`ValidationAttribute` / `IValidatableObject` (`trebovaniya.md` §8). Nothing is
trimmed before validation. Lengths are counted in Unicode code points (as US-001
I-5).

### VR-001 Name

| Rule | Value |
|---|---|
| required | yes |
| length | 1 to 200 characters inclusive |
| edges | must not start or end with a whitespace character (`char.IsWhiteSpace` semantics, Unicode) — rejected, not trimmed |
| characters | any characters, Cyrillic included, **except** Unicode control characters (category `Cc` — line break, tab, …) and format characters (category `Cf` — zero-width space, direction marks, …) anywhere in the name (**OD-002**, resolved) |
| uniqueness | none |
| valid examples | `Ліцей №1`, `DAC`, 200 characters |
| invalid examples | empty; ` Ліцей`; `Ліцей `; 201 characters; `Ліцей
№1`; `Ліцей​№1` |

### VR-002 Domain

| Rule | Value |
|---|---|
| required | yes |
| length | 3 to 253 characters inclusive |
| characters | Latin letters `A–Z`, `a–z`, digits `0–9`, `-`, `.` — nothing else (no space, `@`, `/`, `:`, Cyrillic) |
| dot | at least one `.` |
| scheme / path | rejected by the character rule (`https://…`, `…/path`, `user@…`) |
| IDN | Cyrillic is rejected by the character rule; a label starting with `xn--` (any case) is rejected (**OD-001**, resolved) |
| label structure | dot-separated labels; no empty label (no leading, trailing or double dot); each label 1 to 63 characters; a label neither starts nor ends with `-` (**OD-001**, resolved) |
| case | any case accepted; stored in lower case; comparison therefore case-insensitive |
| uniqueness | across all installations (FR-008) |
| valid examples | `dac.ukr.education`, `DAC.Ukr.Education` (stored `dac.ukr.education`) |
| invalid examples | `ab` (2); `localhost` (no dot); `https://dac.ukr.education`; `admin@dac.ukr.education`; `ліцей.укр`; 254 characters; `.dac.ukr`; `dac.ukr.`; `dac..ukr`; `-dac.ukr`; `dac-.ukr`; a 64-character label; `xn--80a.ukr` |

### VR-003 Client ID

| Rule | Value |
|---|---|
| required | yes |
| characters | ASCII digits `0–9` only (no spaces, signs, separators; non-ASCII digits rejected) |
| length | 10 to 32 digits inclusive |
| leading zeros | allowed and preserved; the value is a string, never parsed as a number *(interpretation I-9)* |
| uniqueness | across all installations (FR-008), ordinal comparison |
| valid examples | `123456789012345678901` (21 digits), `0123456789` |
| invalid examples | 9 digits; 33 digits; `1234 5678 90`; `12345678901234567890a`; `+1234567890` |

### VR-004 Messages

- Each field error names the field and rule in translated, display-safe terms,
  never a stack trace, type name or internal detail (SC-10).
- On a validation or conflict failure the form keeps the values typed (AC-003);
  they are HTML-encoded on output.
- Rejected values are never written to a log line or audit row (FR-014, FR-009).

## 8. Error Handling

| Situation | Status | What the Owner sees | Audit |
|---|---|---|---|
| Any endpoint without a session (Owner exists) | `302` | sign-in page | — |
| Any endpoint before setup | `302` | setup page (US-001) | — |
| Missing/invalid antiforgery token | `400` | error page "page expired" | — |
| Registration / name / client ID: field validation failed | `400` | the form with field errors and typed values | — |
| Registration: domain and/or client ID already registered (pre-check or lost race) | `409` | the form with the conflict error(s) | — |
| Client ID change: already registered elsewhere (pre-check or lost race) | `409` | the form with the conflict error | — |
| Name or client ID submitted unchanged | `302` | detail page | — |
| Success (create, rename, client ID change) | `302` | detail page | succeeded row |
| Unknown identifier or non-UUID route value | `404` | error page "not found" | — |
| Unhandled exception | `500` | error page "internal error" | — |

Expected outcomes (validation failure, conflict, unchanged, not found) are results
of `ControlPlane.Services`, not exceptions (AD-9). The database unique-constraint
violation of a lost race is caught in `ControlPlane.Services` and turned into the
conflict result, identifying which field conflicted.

## 10. Out of Scope

- `AllowedAdmin` entries and the Admin login check (US-003).
- Suspending and resuming, status changes of any kind (US-004); the status push
  (US-006).
- The legitimacy check, `InstanceLicenseCheck`, `ClassroomAgent.Contracts`, and
  the installation reading its identifier from configuration (US-005).
- Anything in a school installation.
- Deleting an `Installation`; changing a domain (never).
- Verifying the client ID or domain against Google or any other service: the
  Control Plane makes no outbound call (SC-13).
- Search, filtering or pagination of the list.
- Viewing the audit log (EPIC-9); the Owner choosing their UI language (US-039).

### Interpretations for human review

Behaviour not literally fixed by the Story or `trebovaniya.md`, derived here from
the conventions cited. Confirmed by the human on 2026-09-16.

- **I-1** The list is ordered by name (case-insensitive), then by domain.
- **I-2** The list is not paginated: API-8 binds collections that can grow
  unbounded; installations are bounded by the Owner's hosting (~10 schools,
  `trebovaniya.md` §6), and the page is a Razor page, not `/api/v1`.
- **I-3** The home page stays as in US-001 plus a link to the installations list.
- **I-4** Successful form submissions redirect (`302`, post/redirect/get) to the
  detail page rather than answering `201`: these are Razor forms, and API-4's
  `201` shape is for `/api/v1` resources.
- **I-5** Detail and edit pages address the installation by its UUID identifier,
  not by an internal numeric key.
- **I-6** "Copied in one action" is a copy button using a script served from the
  host's static files (allowed anonymous since v68); the identifier is also
  selectable text, so nothing depends on the script.
- **I-7** Name and client ID can be changed whatever the status; `trebovaniya.md`
  restricts neither to active installations.
- **I-8** Conflict messages do not name the installation that holds the value;
  the Owner can find it in the list.
- **I-9** The client ID is kept as a digit string, leading zeros preserved.
- **I-10** Validation failures answer `400` and uniqueness conflicts `409` per
  API-5, although these are Razor forms (as US-001 I-10).
