# Требования: Система контроля учебного процесса (dac.ukr.education)

> Черновик на основе анализа Python/Streamlit-прототипа (google_api.py, app.py, db.py, exports.py).
> Целевая реализация: C# / .NET / EF Core.
> v5 — исправлено противоречие: Owner вынесен из AppUser в отдельную сущность
> Control Plane, физически не связанную с БД инсталляций (см. раздел 3, 9).

## 1. Контекст и цель

Учебное заведение использует Google Workspace for Education (домен dac.ukr.education),
учебный процесс организован через Google Classroom. Существующий Python-прототип
синхронизирует данные Classroom в локальную БД и формирует отчёты для учебной части.
Нужна переработка в стабильную .NET-систему.

**Важное разграничение зоны ответственности:** в Google Workspace на домене dac.ukr.education
есть свои администраторы Workspace — они создают аккаунты, формируют группы и т.д. на стороне
Google. Наша программа **не управляет** Google Workspace — она только читает уже готовую
информацию оттуда (курсы, участники, задания, оценки, группы) и работает с ней локально.

**Источник данных:** Google Classroom API через service account с domain-wide delegation
(impersonation от имени пользователя-администратора Workspace). Прямого доступа к AD не
требуется — авторизация и данные идут через Google Workspace Admin API / Classroom API.

## 2. Пользователи и роли

| Роль | Потребности |
|---|---|
| Владелец | Единственная роль на весь сервис (не привязана к домену); одобряет, кто может быть Админом каждой инсталляции; управляет доступом инсталляций (см. раздел 9) |
| Админ (программы) | Полный доступ к настройкам программы: подключение к Google Workspace Admin API / Classroom API (service account, домен), создание учётных записей Декан/Преподаватель; плюс полный доступ на просмотр данных — все курсы, журналы, посещаемость, успеваемость, как у Декана |
| Декан | Обзор всех курсов, преподавателей, посещаемости, успеваемости; выгрузка отчётов; может инициировать синхронизацию |
| Преподаватель | Свои курсы, журналы, материалы, оценки студентов; может инициировать синхронизацию |
| Студент | *Epic на будущее — не в первой версии* |

**Важно:** Владелец, Админ и Декан — роли, существующие только внутри нашей программы
(у Google Classroom нет понятий "Владелец"/"Админ программы"/"Декан"). Преподаватель как
роль в программе связан с преподавателем как участником Classroom, но это две разные
записи (см. раздел 3 — AppUser vs ClassroomParticipant).

### Модель авторизации

- Ролевая авторизация нужна **внутри программы** — для разграничения прав доступа к локальной БД.
- **Админ** проходит вход через Google OAuth (Login via Google) — именно Админ отвечает за
  подключение и настройку доступа к Google Workspace Admin API / Classroom API через
  сервисный аккаунт. Через эти права наполняется локальная БД. **Стать Админом можно
  только если Владелец заранее одобрил email этого человека** (см. раздел 9 — без этого
  шага настройка подключения к Google Workspace недоступна)
- **Декан / Преподаватель** входят по логину/паролю внутри программы (ASP.NET Core Identity).
  Учётную запись создаёт **Админ** вручную (не Владелец — одобрение Владельца требуется
  только для роли Админа, см. раздел 9). Они могут только **инициировать** синхронизацию
  локальной БД с Google Classroom, но не настраивать сам доступ к API.

### Сценарий входа

0. **Владелец** одобряет email конкретного человека как допустимого Админа данной
   инсталляции (раздел 9)
1. **Инициализация:** Админ (с одобренным email) настраивает доступ программы к Google
   Workspace через Google OAuth / service account (домен, credentials, impersonation)
2. Админ создаёт учётные записи для Декана/Преподавателя (логин/пароль)
3. Декан/Преподаватель запускают программу и входят по выданным логину/паролю
4. Инициируют синхронизацию локальной БД (если нужны свежие данные)
5. Видят в локальной БД только то, что положено их роли

## 3. Ключевые сущности (Domain)

- **AppUser** *(Data Plane — БД конкретной инсталляции)* — учётная запись
  пользователя внутри инсталляции: логин, пароль (hash), роль в приложении
  (Admin/Dean/Teacher). Admin — одобряется Владельцем (см. раздел 9) и входит
  через Google OAuth; Dean/Teacher — создаются Админом вручную. Для роли Teacher —
  связана с соответствующим ClassroomParticipant (по email); "свои" курсы —
  это все курсы, где данный ClassroomParticipant есть в ростере с ролью teacher
  (включая со-преподавательство, не только курсы, где он owner — см. Course ниже).
  **Владелец в этой таблице не хранится** — см. Owner ниже
- **Owner** *(Control Plane — отдельный сервис, отдельная БД)* — единственная на
  весь сервис учётная запись Владельца: логин, пароль (hash), задаётся один раз
  при first-run setup Control Plane (ASP.NET Core Identity). Не привязана ни к
  одной инсталляции/домену и физически отделена от AppUser (см. раздел 9)
- **ClassroomParticipant** — участник Classroom, приходит из синхронизации:
  id (Google userId), email, name, роль в Classroom (teacher/student) — эта роль
  не совпадает с ролью в приложении (AppUser)
- **Course** — курс Classroom: id, name, section, description, room, owner (преподаватель,
  создавший курс — основной владелец по данным Classroom API; курс может иметь и других
  со-преподавателей — см. ClassroomParticipant/roster, они тоже видят курс своим, не
  только owner), даты создания/обновления, state (ACTIVE/ARCHIVED/PROVISIONED/DECLINED/
  SUSPENDED), ссылка, связь many-to-many с `Group` (см. ниже — группы, через которые
  Google Workspace добавляет участников в этот курс), папка преподавателя, calendarId
- **Group** — учебная группа, заведённая в Google Workspace: групповой email-аккаунт
  (письмо на этот адрес получают все члены группы). Google Workspace позволяет добавить
  такой групповой email в ростер курса вместо перечисления участников по одному —
  подключение группы к курсу означает одновременное добавление всех её текущих и
  будущих членов в этот курс. `Course.групповые email'ы` — это ссылки на связанные
  `Group`, а не отдельный дублирующийся источник данных
- **CourseWork** — задание или учебный материал курса: заголовок, тип (courseWork/material),
  дата (каскад: scheduledTime → dueDate → updateTime → creationTime)
- **Submission** — сдача задания студентом: userId, courseWorkId, assignedGrade
- **MeetSession** — сессия Google Meet, данные из Admin Reports API (Meet Attendance
  Reports): дата, время начала/конца, участник, длительность присутствия → основа
  посещаемости. *Ограничение: Admin Reports API отдаёт данные с задержкой (обычно
  до 24 часов) — не real-time*
- **SyncState** — статус фоновой синхронизации с Classroom API (running/completed/failed,
  счётчик, последняя ошибка, время последней синхронизации)
- **WorkspaceConnection** — настройки подключения инсталляции к конкретному домену
  Google Workspace: домен, service account credentials, impersonation-пользователь —
  должно быть переносимо/переконфигурируемо Админом на другой домен
- **ReportTemplate** — конфигурируемый шаблон вывода журнала/отчёта (полный / сокращённый /
  приближенный к бумажному академическому журналу), привязанный к существующим
  наработкам пользователя
- **AllowedAdmin** *(Control Plane)* — email Google-аккаунта, допущенного быть Админом
  конкретной инсталляции/домена, кем и когда добавлен Владельцем. Пароль не хранится
- **InstanceLicenseCheck** *(Control Plane)* — результат последней периодической проверки
  инсталляции: статус (активна/приостановлена), время проверки, срок действия локального
  кэша/grace period

## 4. Epics / User Stories

### Epic 1: Синхронизация с Google Classroom
- Как система, я периодически (или по запросу) синхронизирую список курсов, участников,
  групп, заданий/материалов и оценок через Classroom API
- Обработка rate limit (429/5xx) с retry + exponential backoff
- Инкрементальная синхронизация: не загружать заново уже известных пользователей
- Хранение времени последней синхронизации, статуса и ошибок
- Декан/Преподаватель могут вручную инициировать синхронизацию (кнопка), Админ настраивает,
  как и куда синхронизация подключается

### Epic 2: Курсы, участники, группы
- Учебная часть видит список всех курсов с фильтрами (статус, преподаватель, поиск по названию)
- Учебная часть видит преподавателей и привязанные к ним курсы
- Просмотр студентов курса, в т.ч. через привязанные учебные группы
- Отображение групп и их состава

### Epic 3: Журнал успеваемости и печатные шаблоны
- Формирование журнала: студент × (задание/материал с датой) × оценка, за выбранный период
- Разделение "оценивается" (courseWork) и "не оценивается" (material)
- Вывод данных в **полном объёме** (все синхронизированные поля) и в **сокращённом,
  приближенном к бумажному академическому журналу** формате
- Поддержка нескольких настраиваемых `ReportTemplate` (у пользователя уже есть готовые
  разработанные шаблоны) — печать/сборка нескольких шаблонов в единый бумажный журнал
- Экспорт журнала в Excel (по шаблону) и Word

### Epic 4: Посещаемость (Google Meet)
- Интеграция с Admin Reports API (Meet Attendance Reports) для получения фактических данных
  о присутствии на видеовстречах (с учётом задержки данных API)
- Отчёт по посещаемости за период на курс/студента

### Epic 5: Управление БД
- Раздел показывает: общую статистику локальной БД (кол-во курсов, пользователей, групп и т.п.),
  время последней синхронизации, кнопку "Синхронизировать"

### Epic 6: Настройки программы / Админ-панель
- Админ настраивает подключение к Google Workspace: домен, service account, impersonation
- Поддержка одного активного домена Google Workspace за раз, с возможностью
  переконфигурации на другой домен (без мультитенантности "несколько доменов
  одновременно" в первой версии)
- Админ управляет учётными записями Декан/Преподаватель (создание AppUser)

### Epic 7 (будущее): Доступ студентов
- Отдельный Epic вне первой версии

### Epic 8: Владелец и Control Plane
- Владелец авторизуется в Control Plane при первом запуске: логин/пароль, задаётся
  один раз при first-run setup (ASP.NET Core Identity)
- Владелец вручную ведёт список разрешённых Админов по инсталляциям, по email их
  личного/рабочего Google-аккаунта (пароли Админов не хранятся) — **и может в любой
  момент отозвать разрешение**, чтобы приостановить доступ конкретной школы без
  необходимости заходить на её сервер (инструмент управления сотрудничеством, а не
  только защита от посторонних — служебный канал Control Plane ↔ Data Plane и так
  приватный, см. раздел 9)
- Админ инсталляции может завершить настройку подключения к Google Workspace только
  если он есть в списке разрешённых
- Каждая инсталляция периодически (например, раз в сутки) подтверждает свою легитимность
  в Control Plane, с локальным кэшем и запасом прочности на случай недоступности
  Control Plane
- **Режим при истечении grace period** (Control Plane недоступен дольше запаса прочности,
  или Владелец отозвал разрешение): инсталляция переходит в **режим "только чтение"** —
  просмотр уже синхронизированных данных остаётся доступен, но синхронизация и
  административные изменения блокируются, пока легитимность не будет подтверждена заново

## 5. Нефункциональные требования

- **Производительность:** синхронизация не должна блокировать UI — фоновый процесс
  (в .NET — `IHostedService` / `BackgroundService`, а не поток в веб-запросе, как в Streamlit)
- **Надёжность:** устойчивость к сбоям Google API (retry, идемпотентный upsert)
- **Безопасность:** service account credentials — не в репозитории, через secrets/Key Vault/
  переменные окружения; Google OAuth2 — для роли Админ (после одобрения Владельцем);
  Декан/Преподаватель — логин/пароль через ASP.NET Core Identity, учётку создаёт Админ вручную
- **Приватность данных:** журналы и посещаемость содержат персональные данные студентов
  (в т.ч. потенциально несовершеннолетних) — доступ ограничен ролями Декан/Преподаватель/
  Админ; политика хранения и удаления данных — уточнить отдельно перед продакшеном
- **Хранение данных:** переход с SQLite-кэша на SQL Server (или PostgreSQL) + EF Core,
  с учётом роста объёма (несколько лет курсов/оценок)
- **Экспорт:** сохранить поддержку Excel (в т.ч. по существующим шаблонам школы) и Word;
  шаблоны — конфигурируемый ресурс, а не хардкод в коде (как было в прототипе)
- **Мобильная версия:** адаптивный веб-интерфейс (responsive UI), отдельного нативного
  мобильного приложения не требуется
- **Универсальность / переносимость на другой домен:** Админ должен иметь возможность
  переконфигурировать программу на другой домен Google Workspace без переписывания кода —
  домен, credentials, impersonation-адрес вынесены в конфигурацию/настройки, а не
  захардкожены (как сейчас в прототипе: `SERVICE_ACCOUNT_FILE`, `admin@dac.ukr.education`)
- **Развиваемость / поддержка новых версий:** архитектура должна допускать выпуск новых
  версий с дополнительным функционалом без переписывания ядра — модульность
  (Clean Architecture слои, чёткие границы Domain/Application/Infrastructure),
  версионирование EF Core миграций, семантическое версионирование релизов, обратная
  совместимость схемы БД при апдейтах

## 6. Интеграции

- **Google Classroom API** (courses, rosters, coursework, submissions, profiles, groups) —
  через service account + domain-wide delegation
- **Google Admin Reports API** (Meet Attendance Reports) — источник данных о посещаемости
  видеовстреч, с задержкой данных до ~24 часов
- **Google OAuth2** — вход для роли Админ
- Экспорт в Excel/Word — библиотеки уровня .NET (ClosedXML/EPPlus для Excel,
  OpenXML/DocX для Word)

## 8. Архитектурное решение: Server vs Client

**Выбрано:** ASP.NET Core MVC/Razor Pages + REST API (backend отдаёт данные через API,
UI рендерится на сервере/через Razor). Причина выбора — предсказуемость и уже имеющийся
опыт с Controllers-стилем (аналогично Customer Portal), в отличие от Blazor.

**На сервере (backend):**
- Service account credentials и вся логика обращения к Google API (Classroom, Admin Reports)
- Локальная БД (SQL Server/PostgreSQL) + EF Core, вся бизнес-логика (синхронизация,
  журналы, посещаемость, генерация отчётов по шаблонам)
- Аутентификация/авторизация (ASP.NET Core Identity), ролевая модель
- Фоновая синхронизация (`BackgroundService`)
- Генерация экспортов Excel/Word по `ReportTemplate` (готовый файл отдаётся клиенту)
- Настройки WorkspaceConnection (домен, impersonation) — доступны только Админу

**На клиенте (Razor UI):**
- Отображение данных (таблицы курсов, журналов, отчётов), полученных через API
- Формы: фильтры, поиск, выбор периода, выбор шаблона отчёта, форма логина
- Локальное состояние UI (выбранная вкладка, пагинация) — без чувствительных данных
- Кнопка "Синхронизировать" — только триггерит серверный эндпоинт
- Токен сессии — в httpOnly cookie, без хранения пароля или Google credentials на клиенте

Архитектурный слоёный подход — по аналогии с Customer Portal: Domain → Application →
Infrastructure (Google API клиент, EF Core) → API/Presentation (Controllers + Razor).

## 9. Надстройка: Владелец сервиса и Control Plane

**Контекст:** программа будет развёрнута примерно в 10 знакомых школах, во всех случаях
хостинг и сопровождение — на стороне пользователя (далее "Владелец"). Каждая школа —
физически отдельная инсталляция (отдельная БД, отдельный backend-процесс), полностью
согласовано с принципом "одна прога — один доступ к Google Workspace" (раздел 6, 8).
Поверх этого — слой централизованного контроля.

### Модель ролей

- **Владелец** — роль выше Админа, одна на весь сервис (не привязана к конкретному
  домену .education). Владелец:
  - проходит собственную авторизацию при первом запуске: логин/пароль, first-run setup
    (ASP.NET Core Identity)
  - вручную вносит и может отозвать email людей, допущенных становиться Админом той или
    иной инсталляции — это одновременно защита от неконтролируемого распространения
    программы **и** личный инструмент управления сотрудничеством со школами (например,
    быстро приостановить доступ школы, не заходя на её сервер)
- **Админ** — одобряется Владельцем (по email), настраивает подключение конкретной
  инсталляции к своему домену Google Workspace, и далее сам создаёт учётные записи
  Декана/Преподавателя внутри своей инсталляции — одобрение Владельца на это уже
  не требуется

### Архитектурное решение: Control Plane / Data Plane

Вместо мультитенантной БД (одна БД на много доменов) — выбрана схема с физической
изоляцией данных школ и отдельным лёгким управляющим сервисом:

- **Data Plane** — по одной инсталляции (backend + БД) на каждую школу/домен, как и было
  решено в разделе 8. Полная физическая изоляция данных между школами.
- **Control Plane** — общий для всех инсталляций сервис, отвечает за:
  - авторизацию Владельца
  - хранение перечня разрешённых Админов (и к каким доменам/инсталляциям они привязаны)
  - периодическую проверку легитимности каждой инсталляции (см. ниже)

**Сетевая изоляция вместо токенов:** поскольку все инсталляции хостятся только Владельцем
на своей инфраструктуре (не самими школами), канал проверки легитимности **Control
Plane ↔ Data Plane** защищён сетевой изоляцией (VPC/private network, недоступной из
публичного интернета), а не токеном/API-ключом на инсталляцию. Это ограничение
касается только служебного канала Control Plane ↔ Data Plane — сама инсталляция
(веб-UI для Декана/Преподавателя/Админа, Google OAuth) остаётся обычным веб-приложением,
доступным пользователям школы из публичного интернета по HTTPS (см. раздел 8).
*Если в будущем какая-то школа захочет самостоятельный хостинг вне инфраструктуры
Владельца — тогда потребуется отдельный реинжиниринг: токен/API-ключ на инсталляцию
вместо сетевой изоляции служебного канала (сознательно отложено).*

**Назначение периодической проверки:** не столько защита от внешних злоумышленников
(сеть и так приватная), сколько **инструмент Владельца для управления доступом школ** —
возможность оперативно приостановить работу конкретной инсталляции (например, если
школа прекратила сотрудничество), не вмешиваясь вручную в её сервер.

**Периодичность:** не на каждый запрос синхронизации, а периодическая проверка
(например, раз в сутки) с локальным кэшированием результата и запасом прочности.

**Поведение при истечении grace period** (Control Plane недоступен дольше запаса
прочности, или Владелец отозвал разрешение): инсталляция переходит в **режим
"только чтение"** — просмотр уже синхронизированных данных остаётся доступен,
но синхронизация и административные изменения блокируются.

### Идентификация Админа

Пароли Админов в Control Plane не хранятся. Админ и так входит в свою инсталляцию через
Google OAuth — Control Plane хранит только **email** его личного/рабочего Google-аккаунта
как идентификатор в списке `AllowedAdmin`. Проверка на стороне инсталляции: "email,
которым вошёл пользователь, — есть ли он в списке разрешённых для этой инсталляции
у Control Plane?".

**Важно развести два разных email одного Админа:**
- email личного/рабочего Google-аккаунта — используется для входа Админа в программу
  (Google OAuth) и для сверки со списком `AllowedAdmin`
- email service account / impersonation-пользователя — используется системой для
  технического обращения к Google Workspace Admin API / Classroom API конкретного домена

Это разные email в общем случае (могут совпадать, но не обязаны) — не путать при
проектировании `WorkspaceConnection` и `AllowedAdmin`.
